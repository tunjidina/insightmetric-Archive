InsightMetric is a daily tech-trend intelligence system that collects signals from news,
open-source releases and community activity, clusters them into clean topics, and predicts
which ones will recur tomorrow — using simple, transparent models and reproducible pipelines.

Everything runs locally in about a minute, with no API keys and no paid services.

## What it does

- Reads five public RSS feeds each morning — Hacker News, TechCrunch, The Verge, Ars Technica, Wired
- Monitors the release feeds of twelve open-source repositories
- Clusters headlines into topics by keyword overlap, and categorises them against a lexicon
- Scores sentiment locally with VADER — no external service ever sees the text
- Tracks Hacker News points, comments and points-per-hour as a developer-attention signal
- Predicts next-day recurrence with a logistic regression, evaluated on a chronological split
- Serves it all through a six-page Streamlit application

The design constraint that shapes everything: **no paid services and no API keys.** Every
source is a public feed. Sentiment runs locally. The model is small enough to explain on one
slide. If a change to this project requires a credential, it is the wrong change.

## About the numbers in this repository

**The committed dataset is synthetic.** It is generated by `src/collect.py` to exercise the
pipeline end to end. The model metrics you will see — 0.66 accuracy against a 0.56 majority
baseline, ROC-AUC 0.71 — are computed on that synthetic history. They say the plumbing works.
They do **not** say that technology trends are predictable.

Live collection produces real data, and the real figures should be expected to be lower: the
synthetic history is generated by a noisy logistic rule that a logistic regression can in
principle recover, whereas the world is under no such obligation. Please do not cite these
numbers as evidence about anything outside this repository.

## Installation

### Requirements

Python 3.10 or newer, and about 500 MB of disk for the dependency tree (scikit-learn,
pandas and matplotlib account for most of it). No database, no message queue, no cloud
account.

### From source

```bash
git clone https://github.com/<you>/insightmetric.git
cd insightmetric
python -m venv .venv && source .venv/bin/activate     # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

Verify the install by building the synthetic history and training on it — this touches no
network at all:

```bash
python src/collect.py --days 45 --seed 42   # writes data/tech_trends.{csv,parquet}
python src/train.py                         # writes models/, prints metrics
streamlit run Daily_Trends.py               # app on http://localhost:8501
```

`./run_all.sh` does the same three steps in order. If `train.py` prints a test accuracy near
0.66 and the app opens, the installation is sound.

### With Docker

One image serves the app, runs the collector and retrains the model:

```bash
docker compose up -d                        # app on http://localhost:8501
docker compose run --rm collector           # collect a real day into ./data
docker compose run --rm trainer             # retrain from ./data
```

`./data` and `./models` are bind-mounted, so collected rows survive container restarts.
See [`DOCKER.md`](DOCKER.md) for the image design and the reasoning behind it.

### Dependencies, and why each is here

| Package | Why |
|---|---|
| `pandas`, `pyarrow` | The dataset is a parquet file; pandas is the whole data layer |
| `scikit-learn` | Logistic regression, scaling, metrics |
| `feedparser` | RSS/Atom parsing — a local library, not a service |
| `vaderSentiment` | Rule-based sentiment, runs offline, no model download |
| `streamlit` | The application |
| `matplotlib`, `wordcloud` | Figures the app and `eda.py` render |
| `joblib` | Model serialisation |

Versions carry upper bounds in `requirements.txt` so a future major release cannot silently
break a deployment.

## Architecture

Three collectors feed one dataset, which feeds one model and one application. Nothing calls
anything else.

```
┌─────────────────────┐
│  five RSS feeds     │  collect_live.py
│  HN · TC · Verge    │──┐
│  Ars · Wired        │  │
└─────────────────────┘  │
┌─────────────────────┐  │   ┌──────────────────────────────────────┐
│  12 GitHub release  │  ├──▶│  cluster → categorise → sentiment    │
│  Atom feeds         │──┤   │  → rank → label recurrence           │
└─────────────────────┘  │   └──────────────────┬───────────────────┘
┌─────────────────────┐  │                      │
│  HN engagement      │──┘                      ▼
│  points · comments  │        ┌────────────────────────────────┐
└─────────────────────┘        │  data/tech_trends.parquet      │
         │                     │  releases · hn_stories · themes│
         │                     └───────┬────────────────┬───────┘
         ▼                             │                │
  data/raw/<date>/                     ▼                ▼
  (raw feed cache,              features.py →      Streamlit app
   replayable offline)          train.py           (six pages)
                                     │                  ▲
                                     └──────────────────┘
                                    models/recurrence_model.joblib
```

Four properties hold by design, and changes should preserve them:

**Every collector caches its raw response** under `data/raw/<date>/` before parsing. Any day
can be rebuilt exactly with `--offline`, which makes debugging a parsing change a local
operation rather than a re-fetch.

**Feature engineering lives in one module.** `src/features.py` is imported by both the trainer
and the application, so the app can never score rows with different transformations from the
ones the model was fitted on.

**The dataset schema is the contract.** `COLUMNS` in `src/collect.py` is what the app, the
model and the parquet file all agree on. Changing it is a breaking change.

**Collection and serving are separable.** The app only reads files. That is what lets the
hosted deployment stay read-only while a scheduled job elsewhere produces the data.

## Pipeline overview

One collection run, step by step. `src/collect_live.py` orchestrates all of it.

### 1. Fetch

Each feed in `FEEDS` is downloaded with a plain HTTP GET and a descriptive user agent, then
written verbatim to `data/raw/<date>/<source>.xml`. A feed that fails logs a warning and is
skipped; one bad source never aborts a run. In `--offline` mode the cache is read instead of
the network.

### 2. Enrich with Hacker News engagement

`src/hn_trending.py` re-reads the already-cached HN feed and parses each story's points,
comment count and submission time. It computes an engagement score
(`points + ½·comments + 5·points-per-hour`, the last term rewarding stories still
accelerating), logs every story, and logs keywords appearing in two or more stories as that
day's cross-story themes. Points ride along on the HN headlines into the main pipeline.

### 3. Add GitHub releases

`src/github_releases.py` reads twelve release Atom feeds, decodes and classifies each tag as
major / minor / patch / other and as pre-release or not, and keeps a deduplicated log. Only
**stable minor and major releases** are promoted into the day's headlines as a sixth source
named `github`; pre-releases, nightlies, patches and CI refs are logged but never surface as
trends. On a real week, that is roughly two promotions across the whole watchlist.

### 4. Cluster headlines into topics

Titles are tokenised, stopworded and lightly stemmed. Two headlines join the same topic when
they share **at least 2 keywords** *and* those shared words are **at least 20% of the union**
of both keyword sets. The second condition matters: without it, "LibreOffice breaks download
records" and "Microsoft breaks another patch Tuesday record" merge on `{break, record}`.
Clustering is a union-find pass, so chains of pairwise matches merge transitively.

### 5. Categorise

Each topic's keywords are scored against `CATEGORY_TERMS`, a lexicon built from words the
feeds actually use rather than from imagination. Ties resolve in dictionary order, with **AI
deliberately last** — "AI" appears in headlines from every other category and would otherwise
absorb them. A money amount in the headline (`€3B`, `$50M`) is a strong funding signal and
adds weight to Startups. Anything the lexicon cannot place becomes `Other`, which is an honest
answer for the general-interest items that appear on tech feeds.

### 6. Score sentiment

VADER scores headline plus summary — headlines alone are too terse and return zero far too
often. The compound score lands in `[-1, 1]`.

### 7. Rank and truncate

Topics sort by distinct source count, then cluster size, then keyword frequency. The top
`TRENDS_PER_DAY` (10) are kept. Keyword frequency excludes tokens appearing on a quarter or
more of the day's headlines, since a word on every headline carries no information about any
particular trend.

### 8. Label recurrence

The target is whether a topic appears again the next day. Real topics are never word-for-word
identical across days, so the match is **Jaccard overlap ≥ 0.4** on keyword sets rather than
string equality. The most recent day is always unlabelled — its label does not exist yet, by
construction.

### 9. Persist

Rows append to `data/tech_trends.parquet` (and a CSV mirror). Re-running a day replaces it
rather than duplicating it, and the whole history is relabelled on each run so that
yesterday's rows gain their labels once today exists.

## Dataset schema

One row is one trend on one day.

| Field | Type | Meaning |
|---|---|---|
| `trend_id` | string | `sha1(date + slug(topic))[:12]` |
| `date` | date | Collection day (UTC) — the grain of the dataset |
| `collected_at` | timestamp | When the agent ran |
| `topic` | string | Topic name (shortest headline in the cluster) |
| `description` | string | One-sentence summary |
| `category` | categorical | AI, Apps, Cybersecurity, Gadgets, Cloud, Chips, Startups, Policy, Other |
| `sentiment_score` | float [-1, 1] | VADER compound over headline + summary |
| `keyword_frequency` | int | Day-wide weighted keyword mentions |
| `keywords` | string | Pipe-separated top keywords |
| `source_count` | int | Distinct sources covering the topic |
| `sources` | string | Pipe-separated source names |
| `hn_points` | int | Hacker News points; 0 if not on HN, always 0 in synthetic data |
| `rank` | int | Position in the day's list (1 = strongest) |
| `recurred_next_day` | nullable int {0,1} | **Target.** Null for the most recent day |

Three side logs carry the detail the main table summarises: `data/releases.parquet`,
`data/hn_stories.parquet` and `data/hn_trending.parquet`.

## The model

### The question

Given everything observable about a topic today, will it appear in tomorrow's top ten?

### Why logistic regression

Because it is the simplest model that can answer the question, and because on a dataset this
size a larger model would buy noise rather than signal. With standardised inputs, the
coefficients *are* the feature importance — one unit is one standard deviation of the feature,
in log-odds — so no SHAP dependency is needed to explain a prediction. Nothing about the
result is hidden behind the method.

### Features

Eighteen in total: nine numeric, plus one-hot encoding of the nine categories.

| Feature | What it captures |
|---|---|
| `sentiment_score` | Direction of tone |
| `sentiment_abs` | Intensity regardless of direction |
| `keyword_count` | Distinct keywords attached to the topic |
| `keyword_frequency` | Day-wide keyword weight |
| `source_count` | Breadth of coverage |
| `hn_points` | Developer attention |
| `description_length` | Weak proxy for depth of coverage |
| `rank` | The collector's own ordering |
| `days_seen_before` | Momentum: prior days this topic has already appeared |
| `cat_*` (9) | One-hot category. Ordinal codes would impose a false ordering |

### Training procedure

The split is **chronological**, not random: the ten most recent labelled days are held out
and everything earlier trains. This matters more than any modelling choice in the project. The
question is forward-looking, so a random split would put tomorrow's rows in the training set
while asking the model to predict today, and the metrics would flatter it. Short histories
hold out a quarter of available days instead, and training refuses below 40 labelled rows.

Inputs are standardised; class weights are balanced. After evaluation the model is refit on
all labelled rows for deployment, so the app benefits from the full history while the reported
metrics stay honest.

### Results on the synthetic history

| Metric | Value |
|---|---|
| Majority-class baseline | 0.560 |
| Accuracy | 0.660 |
| F1 (positive class) | 0.667 |
| ROC-AUC | 0.709 |
| Confusion matrix `[[TN, FP], [FN, TP]]` | `[[32, 12], [22, 34]]` |

### Reading the coefficients

| Feature | Coefficient | Interpretation |
|---|---|---|
| `rank` | −0.57 | Higher-ranked topics (smaller number) persist |
| `source_count` | +0.30 | Breadth of coverage is the strongest positive signal |
| `keyword_count` | +0.17 | Richer topics stick |
| `description_length` | +0.13 | Weak proxy for depth |
| `sentiment_score` | +0.12 | Slight positive tilt — tone is secondary |

The model recovered the two drivers the synthetic generator was built around (coverage and
rank) and correctly found sentiment to be secondary. `keyword_frequency` carries a small
negative coefficient, which is collinearity with `rank` — rank is partly built from it. On
real data, drop one or the other.

### Known limitations

The target is defined by the collector's own ranking, so "recurred" means "made this agent's
top ten again", not "was still newsworthy". The fuzzy label match at 0.4 both misses genuine
continuations that changed vocabulary and occasionally joins distinct stories that share
words; both add label noise. And `hn_points` is zero throughout the synthetic history, so its
coefficient is zero until live data accumulates — that is expected, not a bug.

## The application

Six Streamlit pages, all reading the same parquet files.

| Page | What it shows |
|---|---|
| **Daily Trends** | Today's topics with a traffic-light recurrence badge, sentiment bars, keyword cloud, dataset download |
| **Weekly Summary** | ISO-week roll-up: persistence leaders, category mix, daily sentiment, per-topic table |
| **Settings** | Category filter and dark-mode toggle, optionally saved to `settings.json` |
| **Compare** | Two categories side by side over time: volume, tone, persistence |
| **Releases** | The GitHub release log with cadence per repository |
| **Hacker News** | Front-page stories by engagement, upvoted-vs-discussed scatter, cross-story themes |

Pages that read generated logs show a "no data yet" notice until the collector has run, which
is the correct state on a fresh clone. Setting `DEPLOYED=1` hides the two single-user features
(file-backed settings, and the theme toggle, which is a server-level switch).

## Configuration

Everything tunable is a module-level constant, deliberately — there is no config file to keep
in sync with the code.

| Constant | File | Default | What it controls |
|---|---|---|---|
| `FEEDS` | `collect_live.py` | 5 feeds | Which sources are read |
| `TRENDS_PER_DAY` | `collect_live.py` | 10 | Topics kept per day |
| `MIN_SHARED_KEYWORDS` | `collect_live.py` | 2 | Clustering: shared keywords required |
| `MIN_CLUSTER_JACCARD` | `collect_live.py` | 0.2 | Clustering: overlap as a share of both |
| `FUZZY_MATCH` | `collect_live.py` | 0.4 | Day-to-day topic matching for the label |
| `CATEGORY_TERMS` | `collect_live.py` | lexicon | Categorisation |
| `INCLUDE_GITHUB` | `collect_live.py` | `True` | Whether releases enter the trend dataset |
| `WATCHLIST` | `github_releases.py` | 12 repos | Repositories monitored |
| `HEADLINE_KINDS` | `github_releases.py` | minor, major | Which releases become trends |
| `MIN_STORIES` | `hn_trending.py` | 2 | Stories a keyword needs to count as a theme |
| `TEST_DAYS` | `train.py` | 10 | Days held out chronologically |

`MIN_CLUSTER_JACCARD` and `FUZZY_MATCH` are the two worth revisiting first once you have real
data: they trade recall against false merges, and the right values depend on your feed mix.

## Running it daily

```bash
python src/collect_live.py --dry-run     # preview today, save nothing
python src/collect_live.py               # collect today and append
python src/collect_live.py --offline     # rebuild a day from cached feeds
```

Move `data/tech_trends.*` aside before your first live run, or synthetic and real rows will
mix in one file. Allow about three weeks before retraining.

Three scheduling options, in the order worth reaching for: the included GitHub Actions
workflow (`.github/workflows/collect.yml`), which collects daily and commits the data; a host
scheduler (Task Scheduler or cron) calling the collector; or the Compose `scheduler` profile
for a self-contained always-on box. [`DEPLOY.md`](DEPLOY.md) covers hosting on Render's free
tier, where the app stays read-only and data arrives through Git.

## Contributing

Contributions are welcome. This is a deliberately small project, and the bar for a change is
that it stays that way: readable, reproducible, and explainable to someone who is not a
specialist. [`CONTRIBUTING.md`](CONTRIBUTING.md) has the long form; this is the summary.

### Good places to start

**New feeds.** Add an entry to `FEEDS`. It must be a public RSS or Atom feed needing no API
key. Say in the PR what the source adds that the existing five do not.

**Better clustering.** Embeddings would very likely beat keyword overlap. The constraint is
that it must still run in under a minute on a laptop, with no GPU and no paid API.

**Lexicon improvements.** `CATEGORY_TERMS` was built from words the feeds actually produced.
Please keep it that way, and say which headlines motivated your additions.

**Modelling.** Better features are more interesting than bigger models. If you propose a
different model, report chronological-split metrics against the current baseline — not a
random split.

**UI.** New pages must render correctly when the logs they read are empty.

### Ground rules

- **No paid services and no API keys.** This constraint is the point of the project.
- **Keep the offline replay working.** Cache raw responses; `--offline` must rebuild a day exactly.
- **Evaluate forward in time.** A random split leaks and inflates the numbers.
- **Comments explain why, not what.** The code already says what it does.
- **Schema changes are breaking.** If you touch `COLUMNS`, say so explicitly in the PR.

### Pull requests

Small and focused beats large and sweeping. Describe what you changed, why, and what you ran
to check it. There is no test suite yet — adding one is itself a welcome contribution.
